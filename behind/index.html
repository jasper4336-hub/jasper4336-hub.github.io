為什麼自己做，而不是用現成的平台

部落格平台很方便，為什麼還要自己做？原因很簡單：我想要一個完全照自己的方式整理的地方。作品要有固定的四段（為什麼做、能做什麼、怎麼做出來、還不夠好的地方），文章要標出依據，課程筆記要能收成合集——這些規則，現成的平台很難照著走。

網站用 Astro 這套工具產生，建好之後是一包純 HTML 檔案，放在 GitHub Pages 上，不需要伺服器，也不用付費。原始碼另外備份在私人的 GitHub repo。就算哪天要換平台，這包檔案搬過去就能用。

版面規則：直角、細線、不加陰影

整個網站只用直角、細線和粗黑線分隔，不用圓角，也不加陰影。標題用襯線字，內文用黑體，強調色只有一種磚紅色。規則少，畫面才不會越做越雜。

規則寫在紙上容易忘，所以我讓程式來守：每次上線前，檢查程式會掃過所有網頁，只要出現圓角或陰影就停下來，不讓它上線。

字標題襯線、內文黑體

讀者可以用 A− / A+ 調整字級，共四段。

色只有一種強調色

深色模式另外定義一組顏色，不是單純反白。

線粗線分區、細線分項

不用圓角和陰影，由檢查程式把關。

內容怎麼管：先標依據，再談好不好看

每篇文章都會標出依據：實測、依官方資料整理，或個人看法。讀者一眼就知道，這段話是我試過的、查來的，還是我自己的想法。

內容都用 Markdown 寫，每篇有一個不顯示在畫面上的編號（文章 P001 起、作品 W01 起），方便之後整理。還沒寫完的文章標成草稿，只在我自己的電腦上看得到，正式網站不會出現。文章的「類型」說它怎麼寫（作品介紹、應用、學習筆記、心得），「標籤」說它寫什麼主題，兩者分開，不重複。

自動把關：上線前的七道檢查

網站越做越大，靠眼睛檢查一定會漏。所以每次上線前，部署程式會依序跑完這些檢查，任何一項沒過就停下來：

檢查擋下什麼
版面規則圓角、陰影
個資疑似學號、手機號碼、學校信箱，以及還沒查證完、留著標記的內容
標點中文句子裡出現半形的逗號、冒號、問號或括號（英文、數字、網址與程式碼不算）
外部字型又改回向 Google Fonts 載入字型（字型應該放在自己的網站，理由見下文）
連結站內連結或圖片找不到檔案、同頁跳轉找不到對應段落
草稿草稿被建置出來；沒有任何頁面用到的圖片（例如草稿的封面）也不公開
手機與平板版面用無頭瀏覽器以 320 到 1280 像素的多種寬度打開每一頁，檢查有沒有內容超出畫面、圖片有沒有被壓扁

最後一項是踩過坑才加上的，下面會說。

閱讀與搜尋：讓長文章讀得下去

課程筆記一篇常常超過五千字，所以閱讀工具比裝飾重要。上方的段落列會跟著你讀到哪一段而標示；寬螢幕時，左側會出現固定的目錄。文章最後有上一篇、下一篇和「你可能也想讀」，合集裡的文章則接回合集頁。

站內搜尋用的是 Pagefind：網站建好時，順便把文章與作品的內文做成索引檔，一起放上網站。搜尋時在讀者的瀏覽器裡比對，不需要後端。中文斷詞後，摘要會在字和字之間多出空格，我在顯示前把它們拿掉，讀起來才自然。

字型、留言、瀏覽數：不架後端，也要顧到讀者

這三樣功能，一般網站都靠伺服器或大型平台處理。這個網站沒有後端，所以每一樣都要先想清楚：資料放在哪裡、讀者要付出什麼、哪天服務停了會怎樣。

字型：放在自己的網站

一開始字型是向 Google Fonts 載入的，後來改成放在自己的網站。理由有三個：讀者打開網頁時，不用再連到另一家公司的伺服器；網站搬家時，字型可以整包帶走；外部服務改版或停掉，也不會影響這裡。

難處在中文字型很大，完整的一套動輒十幾 MB。我的做法是每次建置時，程式先收集網站實際用到的字（目前約一千三百字），再把開源的思源字型(Noto)裁成只含這些字。三個字型檔加起來約 900 KB，讀者第一次載入後，瀏覽器就會留著重複使用。

代價是：讀者在搜尋框打了網站沒用過的字，那幾個字會改用系統字型顯示。新文章用到的新字，建置時會自動加進去，不用手動處理。

這樣做也有幾件事要顧好。字型越來越大時，建置會提醒我（超過 1.5 MB 就要拆檔）；字型檔名帶有依內容產生的編號，內容一變檔名就變，讀者不會拿到缺字的舊檔；原始字型固定在同一個版本，並核對檔案指紋，換一台電腦建置，結果也一樣。

字型：思源黑體(Noto Sans TC)、思源宋體(Noto Serif TC)、Playfair Display，皆採 SIL Open Font License 1.1 授權，授權條款：Noto Sans TC、Noto Serif TC、Playfair Display。Playfair Display 的授權把名稱列為保留字，所以保留原檔、不裁切。

留言：存在網站自己的 GitHub 討論區

留言用的是 Giscus。每篇文章對應網站公開 repo 裡的一則 GitHub Discussion，留言就存在那裡。好處是免費、不用自己架後端，留言資料也在自己的帳號底下，要整理或刪除都由我決定。外觀另外改成網站的直角、細線與配色，深淺色也會跟著切換。

代價是：讀者要有 GitHub 帳號才能留言。對不寫程式的讀者來說，這個門檻不低。所以聯絡按鈕一直留在頁首：不想註冊的人，寫信一樣找得到我。

瀏覽數：不用 cookie 的計數

瀏覽數用的是 GoatCounter。它不用 cookie，也不建立讀者的個人資料，所以網站不用跳出「同意使用 cookie」的視窗。文章與作品頁會顯示該篇的瀏覽次數，頁尾顯示全站的總次數。同一個人短時間內重複打開同一頁只算一次，我在自己電腦上預覽也不會被算進去。

代價是：數字會比實際少一些，因為有些擋廣告的外掛會擋下計數。另外，數字是向 GoatCounter 讀來的，讀不到時就直接不顯示，不影響閱讀。對我來說，這個數字是用來判斷哪些主題值得多寫，不是拿來比較的。

踩過的坑：手機上的三個問題

網站在電腦上看起來都很好，用手機打開才發現問題。三個坑的原因不同，結果卻很像：畫面被撐寬或變形。

  1. 表格把整頁撐寬。文章欄位在格狀版面裡設了自動置中，寬度就改成「依內容決定」，一張寬表格就把整欄推出螢幕，手機只好把整頁縮小，右邊多出一條空白。改法是讓文章欄位明確填滿欄寬，表格自己左右捲動。
  2. 長網址沒有地方換行。資料來源裡的網址沒有空格，瀏覽器找不到斷行的位置。改法是允許網址在任何位置換行。
  3. 圖片被壓扁。圖片標了原始寬高，避免載入時畫面跳動；但縮到手機寬度時，只有寬度跟著縮，高度還是原本的數字。改法是讓高度跟著比例自動計算。

修好之後，我把「多種寬度打開每一頁」寫成自動檢查，加進上線前的流程。同樣的錯，不應該靠讀者再發現一次。

和 AI 的分工：我決定，它動手，我驗收

這個網站的程式，大部分是我和 Claude Code 一起寫的。分工很清楚：要做什麼、怎麼取捨，由我決定；它負責把想法變成程式碼；最後由我在真的網頁上打開、操作、確認。

為什麼一定要親自驗收？因為「程式說成功」和「網頁真的正常」是兩件事。這個網站每次上線，都會實際抓一次線上的頁面，確認新功能真的出現、草稿真的沒有外流，才算完成。

這一頁會跟著網站的做法一起更新。想聊聊網站怎麼做，歡迎來信。
